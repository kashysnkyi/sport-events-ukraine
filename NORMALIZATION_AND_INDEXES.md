# Нормалізація та індекси

## Рівні моделі

Концептуальний рівень описаний ER-діаграмою у `sports_events_portal.dbml`. Він показує предметну область спортивних подій, учасників, команд, категорій, змагань, матчів, результатів, локацій і спонсорів.

Логічний рівень описаний реляційними таблицями, первинними ключами, зовнішніми ключами, унікальними обмеженнями та зв'язками.

Фізичний рівень описаний у `schema.sql` для PostgreSQL. Він містить типи даних, `CHECK`, `UNIQUE`, часткові індекси, GIN індекс, функції, тригери та подання.

## Нормальна форма

### Перша нормальна форма

Кожне поле містить одне атомарне значення. Наприклад, у `event_registration` зберігається одна заявка одного спортсмена на одну категорію. Список категорій не записується в одному текстовому полі, для цього існує окрема таблиця `event_category`.

### Друга нормальна форма

Залежності винесені в окремі сутності. Дані виду спорту зберігаються у `sport`, дані локації у `venue`, дані спортсмена у `athlete_profile`, а зв'язок спортсмена з командою у `team_member`. Атрибути зв'язкових таблиць описують саме цей зв'язок.

### Третя нормальна форма

Неключові атрибути не залежать транзитивно від ключа іншої сутності. Назва міста і місткість локації не дублюються в `sport_event`, а зберігаються у `venue`. Назва виду спорту не дублюється в події, а отримується через `sport_id`. Назва категорії не дублюється у заявці, а отримується через `category_id`.

## Які аномалії усуває модель

- Аномалія вставки: можна створити вид спорту, локацію або категорію до створення першої заявки.
- Аномалія оновлення: зміна назви локації виконується в одному рядку `venue`.
- Аномалія видалення: видалення останньої заявки не видаляє категорію, подію або спортсмена.
- Аномалія вибірки: подання об'єднують пов'язані таблиці та повертають узгоджені дані для каталогу й результатів.

## Індекси

У схемі використані різні типи індексів:

- `ix_event_status_start` - частковий B-tree індекс для фільтрації опублікованих подій за статусом і датою.
- `ix_event_name_trgm` - GIN індекс з `pg_trgm` для пошуку фрагмента назви події.
- Унікальні індекси на зв'язках `event_category(event_id, code)`, `team_member(team_id, athlete_id)` та `event_registration(category_id, athlete_id)` захищають від дублювання.
- Часткові індекси з умовою `deleted_at IS NULL` не включають soft deleted записи у робочий пошук.

Перевірка індексів у pgAdmin:

```sql
SELECT indexname, tablename, indexdef
FROM pg_indexes
WHERE schemaname = 'sports'
ORDER BY tablename, indexname;
```

Перевірка використання індексу для каталогу:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM sports.sport_event
WHERE deleted_at IS NULL
  AND status = 'published'
  AND starts_at >= now();
```

Перевірка пошуку за фрагментом назви:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name
FROM sports.sport_event
WHERE deleted_at IS NULL
  AND name ILIKE '%кубок%';
```
